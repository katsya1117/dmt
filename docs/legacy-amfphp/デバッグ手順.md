# index.html から リモートPHP(AMFPHP) をデバッグする手順

`docs/legacy-amfphp/` にある `index.html` / `webService/...` は、客先サーバー上に実物がある既存コードをOCR経由で復元したもの。ここでは、その**実物（リモートのPHP群）**に対して、手元の`index.html`から実際に通信して動作確認する手順をまとめる。

## ローカルDocker環境で動作確認済み（2026-08-17）

客先の本番サーバーには当然アクセスできないが、Dockerで**再構成したPHPファイル自体**（`DBConnection.php`・`Log.php`・`HelloWorldService.php`）が実際に動くかどうかはローカルで確認できた。

- `php:8.3-cli`イメージで4ファイルとも構文エラー無し（`php -l`）
- MySQLコンテナ＋`t_car`テーブルを用意し、AMFPHP本体（未入手）の代わりに直接`HelloWorldService`を呼び出す簡易ハーネスで`ShowHello()`/`callParametersMethod()`/`callCarInformation()`の3メソッドをすべて実行 → 正常動作、日本語（`テストカー001`）もJSON経由で正しく往復することを確認
- `Log.php`のログ出力も実際にファイルへ書き込まれることを確認（末尾が原文で途切れていたため推定で補完した`logout()`の続きも含めて問題なく動作）

**この過程で見つかった重要な仕様（実物のフォルダ構成と合わせて要確認）**：
`HelloWorldService.php`の`require_once '../config.php';`は、**PHPを実行した時のカレントディレクトリ（CWD）基準**で解決される（Node.jsの`require`のようにファイル自身の場所基準ではない）。Webサーバー経由の実行では、CWDは通常「最初にリクエストされたスクリプト（＝`gateway.php`）のあるディレクトリ」になるため、`webService/amfphp/`が基準になり、`../config.php`は`webService/config.php`を指す（＝ユーザーが最初に教えてくれたフォルダ構成と一致）。ローカル検証でも、ハーネスを`gateway.php`と同じ`webService/amfphp/`に置いて実行することで、この動きを再現できた。**もし実際のサーバーで`Services`配下から直接叩くような構成になっていると、このrequireが失敗する**ので、本番の挙動と食い違ったらまずここを疑うとよい。

## 前提として確認しておきたいこと

デバッグ方法は「PHPサーバーにどこまでアクセスできるか」で変わる。まず以下を確認する。

1. **リモートサーバーへのネットワーク到達性**：社内から客先サーバーへアクセスできる経路があるか（VPN、専用線、単にインターネット経由で叩けるか等）
2. **gateway.phpの実際のURL**：例 `https://customer-server.example.com/webService/amfphp/gateway.php` のような、実際にアクセスできるURL
3. **サーバーへのファイル配置権限**：`index.html`をサーバー上に一時的に置かせてもらえるか（SFTP/SSH等）
4. **サーバーのログを見る権限**：`Log.php`が書き出すログファイルを確認できるか

これらが分からない場合は、先に運用担当・客先の窓口に確認するところから始める必要がある。

## 方法A：index.htmlをリモートサーバーに置いて動かす（推奨・最短）

**理由**：`index.html`内のfetch呼び出しは相対パス（`../webService/amfphp/gateway.php`）で書かれている。`index.html`をサーバー上の正しい位置（`Example/index.html`）に置けば、このパスがそのまま機能する。ブラウザから見て「同じオリジン（同じサーバー）」への通信になるため、CORS（後述）の問題も起きない。

### 手順
1. `docs/legacy-amfphp/index.html`を、サーバー上の`Example/index.html`の場所へアップロードする（本物のフォルダ構成が今回もらった資料の通りであれば、`webService/`と同じ階層に`Example/`フォルダがある想定）
2. ブラウザで `https://customer-server.example.com/Example/index.html` のようなURLを開く
3. 各ボタン（`call hello world server`等）を押して動作を確認する

### 注意点（重要）
- **客先の本番サーバーに無断でファイルを置かない**。テスト用に一時ファイルを置いてよいか、置く場所（本番と混ざらない検証用フォルダの有無）を事前に確認する
- 動作確認が終わったら、置いたテスト用ファイルは片付ける

## 方法B：index.htmlは手元のPCで動かし、リモートのgateway.phpだけ叩く

方法Aが難しい場合（サーバーにファイルを置けない等）の代替案。ただし手間とリスクが増える。

### 課題1：相対パスが使えない
`index.html`を手元のPCから開くと、`../webService/amfphp/gateway.php`という相対パスは手元のPC上のパスとして解釈されてしまい、リモートには届かない。**一時的に**fetchのURLを絶対URLに書き換える必要がある。

```js
// 元
const response = await fetch("../webService/amfphp/gateway.php", { ... });
// デバッグ用に一時的にこう変える
const response = await fetch("https://customer-server.example.com/webService/amfphp/gateway.php", { ... });
```

### 課題2：file://で直接開くと動かないことが多い
`index.html`をダブルクリックしてブラウザで直接開く（`file://`から始まるURLになる）と、fetchがブラウザのセキュリティ制限に引っかかりやすい。簡易HTTPサーバー経由で開く。

```bash
# index.htmlがあるフォルダで実行（Node.jsが入っていれば使える）
npx serve .
# もしくはPythonが入っていれば
python3 -m http.server 8080
```
表示されたURL（例：`http://localhost:8080`）をブラウザで開く。

### 課題3：CORS（クロスオリジン制約）
手元のPC（`http://localhost:8080`）からリモートサーバー（`https://customer-server.example.com`）へfetchするのは「別オリジンへの通信（クロスオリジンリクエスト）」に当たる。リモートのPHPサーバーが`Access-Control-Allow-Origin`というレスポンスヘッダーを返していない場合、ブラウザがレスポンスをブロックしてしまう（Networkタブにはリクエストが届いて応答も見えるのに、JS側では`fetch`が失敗する、という分かりにくい症状になる）。

- リモート側にCORS設定を追加してもらえるなら、それが一番安全な解決策
- 追加してもらえない場合、恒久対応ではなく**その場限りのデバッグ**として、ブラウザの拡張機能等でCORSを無効化する方法もあるが、セキュリティを下げる操作なので客先の本番サーバーに対しては非推奨。**基本は方法A（サーバー上で動かす）を優先する**

## ブラウザの開発者ツールでの確認方法

1. ブラウザの開発者ツール（Chromeなら`F12`または`Cmd+Option+I`）を開く
2. **Networkタブ**：ボタンを押した時に送られる`gateway.php`宛てのPOSTリクエストを選び、
   - `Payload`（or `Request`）タブで送信したJSON（`serviceName`/`methodName`/`parameters`）を確認
   - `Response`タブで実際に返ってきた中身を確認
3. **Consoleタブ**：`index.html`には元々`console.log(result)`や`console.error(error.message)`が仕込まれているので、そこに結果やエラーが出る

### レスポンスがJSONとして解釈できない場合
PHP側でエラーが起きると、JSONではなくPHPのエラーメッセージ（HTML）がそのまま返ってくることがある。この場合`response.json()`が失敗し、`catch`ブロックに入ってしまう（`エラーメッセージが読めない`という状態になりやすい）。原因を見るために、一時的に生のテキストとして確認するとよい。

```js
// デバッグ用に一時的に追加
const raw = await response.clone().text();
console.log("raw response:", raw);
```

## サーバー側のPHPデバッグ環境

ブラウザ側（Network/Console）だけでは「PHPが結局何をして失敗したか」までは分からない。PHP側の設定・ツールは、必要なアクセス権のレベルに応じて3段階ある。

### レベル1：php.iniの設定（追加ツール不要・一番手軽）
- `display_errors = On`：PHPのエラーをレスポンスにそのまま出す。これが`Off`だと、エラー時に空のレスポンスや不可解な500だけが返り、原因が全く見えない
- `error_reporting = E_ALL`：警告・notice含めて全部拾う
- `log_errors = On` ＋ `error_log = /path/to/php-error.log`：エラーをファイルにも残す。`Log.php`（このアプリ独自のログ機構）が動く前にPHP自体が構文エラー等で落ちるケースは、こちらでしか見えない

php.iniを直接編集する権限が無くても、`gateway.php`の先頭に一時的に以下を足せば同じ効果が得られる（**確認が終わったら必ず元に戻す**）。

```php
<?php
ini_set('display_errors', '1');
error_reporting(E_ALL);
```

### レベル2：ログファイルの閲覧権限
`Log.php`が書き出すログ（書き込み先は`config.php`の`LOG_FOLDER`/`LOG_PATH`/`LOG_FILE`という定数次第、まだ内容未入手）や、レベル1の`error_log`で指定したファイルを見るには、サーバーへのSSH等のファイル閲覧権限が必要。ブラウザ側からは分からない内部エラーの原因究明に役立つ。

### レベル3：Xdebug（ステップ実行できる本格デバッガ）
ブレークポイントを置いて1行ずつ処理を追える、JSでいうChrome DevToolsのデバッガに相当するもの。**初めて使う場合の詳しい手順は別ファイル [Xdebugセットアップ手順.md](./Xdebugセットアップ手順.md) にまとめた**（仕組みの説明、サーバー側インストール、SSHトンネル、VSCode設定、実際の使い方、トラブルシューティングまで一通り記載）。

概要だけ書くと、必要なものは以下の通り：
- サーバーへの**root/SSHアクセス**（拡張機能のインストールが必要なため）
- PHPの拡張機能`Xdebug`をサーバーにインストールし、`php.ini`に接続設定を追加
- サーバーから開発者のPC（ポート9003）への接続経路。直接つながらないことが多いため、SSHポートフォワーディングでトンネルを掘る
- VSCode側：「PHP Debug」拡張機能をインストールし、`launch.json`でポート・パスマッピングを設定

**懸念点**：`docs/legacy-amfphp/`が指している対象は客先の本番サーバー。Xdebugは常時有効だと処理速度が落ちるため、本番に入れる拡張機能としては重く、セキュリティ的にも望ましくない。可能なら検証用の別環境（ステージング）を用意してもらい、そちらにだけ入れるのが望ましい。本番しか無い場合は、レベル1・2（`display_errors`設定＋ログ閲覧）にとどめるのが安全。

## よくあるつまずきポイントまとめ

| 症状 | 考えられる原因 |
|---|---|
| `fetch`が失敗する（Networkタブにリクエストすら出ない） | URLの綴り間違い、`file://`から直接開いている |
| Networkタブには出るがJSでエラーになる | CORSでブロックされている（方法Bの課題3） |
| `response.json()`で例外になる | サーバーがJSONでなくHTMLのエラーページを返している（PHPのエラー） |
| `404 Not Found` | `gateway.php`のパスが違う、サーバー上のフォルダ構成が資料と異なる |
| `500 Internal Server Error` | PHP側の実行時エラー。サーバーのログを確認する |
| `callCarInformation`だけ失敗する | DB接続（`config.php`のDB_HOST等）が未設定/間違っている可能性 |

## 推奨の進め方

1. まず**方法A**（index.htmlをリモートサーバーに置く）を、客先の許可を得た上で試す。相対パス・CORSの問題が両方回避できるので一番簡単
2. サーバーにファイルを置けない事情がある場合のみ**方法B**を検討する
3. どちらの場合も、うまく動かなかったら「Networkタブの生レスポンス」と「サーバー側のログ」の両方を見て原因を切り分ける
