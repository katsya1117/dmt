# エラー対応の手順とノウハウ

（作成: 2026-10-07）

エラーにハマって長時間進まなくなる事態を避けるための、詰まった時に順番に確認する手順のまとめ。個別の技術の使い方は関連ドキュメント（末尾）を参照。

## 基本の心構え

- **推測で直さない**。まず「本当に何が起きているか」を確認してから手を動かす
- **一度に複数箇所を変えない**（変数を1つずつ切り分ける。同時に変えると、直っても何が効いたか分からなくなる）
- 「動くはずなのに動かない」は大抵、**思っている前提が崩れている**（キャッシュ・再起動漏れ・設定ファイルの取り違え等）。コードのロジックを疑う前に、まず前提を疑う

## 詰まった時に確認する手順

### 1. エラーメッセージを正確に読む

省略せず全文を読む。スタックトレースは一番深い（自分のコードに近い）行から見る。エラーメッセージは**意訳せず原文のまま**検索する（検索エンジン・ドキュメント両方で、要約した言葉で検索すると関連する情報に当たりにくい）。

### 2. 再現性を確保する

毎回同じ手順で再現できるか確認する。再現しないと、直せたかどうかの判断ができない。再現できたら、関係ない部分を削って**問題が起きる最小構成**に切り詰める。

### 3. 「本当に今の変更が反映されているか」を疑う（一番ハマりやすいパターン）

今回実際に時間を取られた教訓。コードのロジックを疑う前に、まずここを確認する。

- **ビルド・再起動を忘れていないか**：Dockerイメージを再ビルドし忘れていないか（ホストのファイル編集だけでは、既にビルド済みのコンテナには反映されない。`mock/php-server`のDockerfileは`COPY`でファイルを焼き込む構成なので要注意）。php.ini等の設定ファイルを編集した後、サービス（Apache/php-fpm）を再起動したか
- **本当に意図した設定ファイルが読み込まれているか**：CLI用とWebサーバー用で別のphp.iniを読んでいることがある。`phpinfo()`の「Loaded Configuration File」で確認する（詳細: `docs/PHPデバッグログ設定.md`）
- **キャッシュが古いものを返していないか**：OPcache、vite/webpack等のビルドキャッシュ、ブラウザキャッシュ。「ファイルを直したのに動作が変わらない」はこれが非常に多い

### 4. ログ・出力を一次情報として確認する（推測より先に確認する）

- エラーが実際にどこに出力されているか特定する（`docs/PHPデバッグログ設定.md`参照）。「ログに出ていない」＝「エラーが起きていない」ではなく、**想定と違う場所に出ている可能性が高い**（httpd/php-fpm/自分のerror_logのどれに出るかは設定次第）
- 自分でログ・`console.log`を足して、**どこまで処理が実際に進んでいるか**を確認する。憶測で「ここが原因だろう」と決めつけず、通過したかどうかを1箇所ずつ確かめる

### 5. 1つずつ仮説を立てて検証する

「たぶんこれが原因」と思ったら、その仮説だけを確認する小さな確認をする（コードを直す前に、まず仮説が正しいかを確認する）。複数の仮説を同時に試さない。1つ変えて結果を見る、を繰り返す。

### 6. 外部ライブラリ・フレームワークの「1回しか使えないもの」に注意する

Fetch APIの`Response.body`は1回しか読めない（`res.json()`を2回呼ぶと`Body is unusable: Body has already been read`になる）。イテレータ・ストリームなど、他にも「消費したら使えなくなるもの」は多い。**「2回目にだけ失敗する」「ログを1行足したら急にエラーが出るようになった」というエラーはこれを疑う**。

### 7. デバッガーの基本的な癖を理解しておく

- ブレークポイントは「その行を実行した直後」ではなく**「その行を実行する直前」**で止まる。置いた行で変数に代入している場合、止まった瞬間はまだその代入は実行されておらず未定義に見える（1行ステップオーバーすれば見える）
- リモートデバッグ（Xdebug等）では、パスマッピングの設定がズレていると「エディタ上の行」と「実際の実行位置」がズレて表示されることがある

### 8. 時間を区切る（タイムボックス）

同じ問題に30分〜1時間詰まって進展が無ければ、一度離れる。別の角度から当たる（ドキュメント化する、人に説明してみる、一晩置く）方が、ハマったまま延々続けるより大抵早い。

### 9. 解決したら、原因と対処を記録する

「何が原因で、どう直したか」を一言でも`docs/`配下に残す。同じ沼に二度落ちないための、一番安い投資。

## ゾンビ・取り残されたプロセスの対処（ポート競合等）

VS Codeのデバッグを停止ボタンで終了しても、`preLaunchTask`で起動した**バックグラウンドタスク**（例：Viteの`yarn dev`）は自動では終了しない（デバッグセッションのライフサイクルに紐付いていないため）。ポートを掴んだまま残り、次回起動時にポート競合でハマる原因になる。

### まずVS Code自体に殺させる（OS差が無く一番確実）

コマンドパレット（Mac: Cmd+Shift+P / Windows: Ctrl+Shift+P）→ **「Tasks: Terminate Task」** → 該当タスクを選ぶ。

**ただしこれが効くのは「VS Codeがタスクとして認識して起動したプロセス」だけ**。`tasks.json`経由（`preLaunchTask`/`postDebugTask`、または手動の「Run Task」）で起動したものはここに一覧で出てくるが、**ただのターミナルパネルで自分でコマンドを打って起動したプロセスは「タスク」として追跡されていないため一覧に出てこない**。その場合は、そのターミナルパネルで`Ctrl+C`するか、パネル自体を閉じる（ゴミ箱アイコン）。

### OSのコマンドでポート番号から探して殺す（タスクとして追跡されていない時用）

| | Mac/Linux（zsh/bash） | Windows |
|---|---|---|
| 使用中のプロセスを探す | `lsof -i :3000` | `netstat -ano \| findstr :3000` |
| PIDを指定してkill | `kill <PID>` | `taskkill /PID <PID> /F` |
| ポート指定で一撃 | `kill $(lsof -ti :3000)` | PowerShell: `Stop-Process -Id (Get-NetTCPConnection -LocalPort 3000).OwningProcess -Force` |

Windowsの`netstat -ano`は、該当ポートの行の一番右の列がPID。それを`taskkill /PID <その番号> /F`に渡す2段階になる（Macの`lsof -ti`のように1行で済ませる標準コマンドはcmdには無いが、PowerShellなら上記の1行で可能）。
